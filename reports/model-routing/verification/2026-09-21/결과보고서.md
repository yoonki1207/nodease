# 범용 LLM 라우팅의 단일 모델 수렴 검증

**과거에 한 모델로 수렴한 현상은 실제 기록에서 확인됐다. 이후 이를 막기 위한 설계 변경도 확인됐다. 다만, 정확한 자체 판단으로 여러 요청에 적절한 모델을 선택하게 됐다는 의미의 ‘해결 완료’는 입증되지 않았다. 이번 새 실험에서도 분류기는 합격하지 못했다.**

검증 대상 운영 코드는 `9ad27d5abceb527fa32e6612ffe6b6917450cef5`다. 기존 설명 문서를 사실로 전제하지 않고, 보관된 실행 JSON, Git 변경 이력, 실제 코드, 새 실험과 원격 PostgreSQL 테스트를 대조했다. 이번 작업에서는 운영 알고리즘이나 합격 기준을 바꾸지 않았다.

**1. 무엇이 실제로 발생했나**

여기서 ‘Judge’는 요청을 보고 필요한 모델이나 능력을 판정하는 외부 LLM이고, ‘로컬 분류기’는 그 판정을 학습해 외부 판정 호출을 줄이려는 작은 학습 모델이다.

| 보관 실험 | 처음 외부 Judge가 판단한 50건 | 이후 로컬 분류기가 판단한 요청 | 확인되는 사실 |
|---|---|---|---|
| 2026-07-20, 첫 70건 실험 | `gpt-4.1-mini` 42건, 나머지 모델 8건 | 20건 모두 `gpt-4.1-mini` | 로컬 판단이 한 모델로 쏠렸다. |
| 같은 날 출력 조건을 분리한 80건 실험 | 6개 모델로 나뉘었고 `gpt-5-mini`가 24건으로 최다 | 30건 모두 `gpt-5-mini` | 출력 조건을 바꾼 뒤에도 쏠림은 남았다. |
| 2026-07-22, 수정 후 학습 100건 | 외부 Judge가 전체 100건 판단 | 로컬 판단 0건 | 로컬 전환이 차단된 결과이며, 로컬 라우팅 성공 사례는 아니다. |

기존 JSON을 다시 집계하고 원본 파일의 SHA-256도 남겼다. [재집계 결과](/Users/hong-yoonki/Desktop/krafton/final-project/yoonki1207-nodease/reports/model-routing/verification/2026-09-21/historical-evidence.json)

첫 실험은 JSON 형식 준수와 워크플로 실행 성공률이 모두 100%였지만, 별도 답변 품질 평가의 통과율은 55.7%, 즉 70건 중 39건이었다. **실행이 끝났다는 사실과 답이 맞았다는 사실은 달랐다.**

**2. 원인: 어떤 구조가 이 현상을 만들기 쉬웠나**

**첫째, 필요한 능력을 배우기보다 Judge가 자주 고른 모델 이름을 직접 배웠다.** 당시 분류기는 Judge가 선택한 모델 ID를 정답으로 삼았다. 첫 50개 정답 가운데 42개가 같은 모델이면, 분류기가 여러 요청에 그 모델을 선택하도록 학습 압력이 집중된다. 또한 이 분류기 안에서 계산한 가장 큰 확률을 자신감으로 사용했다. 그 값이 높다는 사실만으로 새로운 요청에서도 답이 정확하다는 보장은 없었다. 이 구조는 [당시 학습 코드](https://github.com/yoonki1207/nodease/blob/c24596c/apps/workflow_engine/services/model_routing_incremental_learning.py#L31)에서 확인된다.

불균형한 정답과 이 학습 구조가 수렴을 일으켰다는 설명은 두 실험의 관측과 강하게 일치한다. 다만 당시 코드를 동일 데이터로 다시 실행하면서 정답 분포만 바꾸는 대조 실험까지 한 것은 아니다. 따라서 이것을 유일한 원인으로 확정하지는 않는다.

**둘째, 로컬 분류기에게 판단을 넘기는 기준이 의미상의 정확성을 충분히 검사하지 않았다.** 당시에는 50개 이상 학습했는지, Judge가 두 종류 이상의 모델을 골랐는지, 실행·출력 형식·후속 처리 등이 성공했는지를 확인했다. 로컬 예측이 정답과 얼마나 일치하는지, 위험한 요청을 낮게 평가하는지, 실제 예측이 한 종류로 굳어졌는지를 충분히 검사하지 않았다. [당시 전환 조건](https://github.com/yoonki1207/nodease/blob/c24596c/apps/workflow_engine/services/model_routing_incremental_learning.py#L153)

첫 실험이 답변 품질 55.7%인 상태에서도 로컬 판단으로 전환됐다는 기록은 이 검증 공백을 실제로 보여 준다.

**셋째, 출력 형식이나 프롬프트 조정만으로는 근본 문제가 사라지지 않았다.** 출력 조건을 분리한 뒤 다수 모델은 `gpt-4.1-mini`에서 `gpt-5-mini`로 바뀌었고 품질 지표도 좋아졌다. 그러나 로컬 판단 30건은 여전히 한 모델에 몰렸다. 따라서 특정 모델이나 출력 형식 하나만의 문제로 설명하기 어렵다.

보관 JSON에는 실행 당시 Git revision이 기록돼 있지 않다. 실행 시각과 artifact 종류를 Git 이력과 대조했지만, 특정 커밋이 당시 실행 파일과 완전히 같았다고 증명할 수는 없다. 코드 구조에 관한 사실과 해당 실행의 원인에 관한 추론을 구분해야 하는 이유다.

**3. 해결: 실제로 무엇을 바꿨나**

1. **모델 이름 대신 요청에 필요한 능력을 학습하도록 바꿨다.** 작업이 얼마나 복잡한지, 판단이 미치는 영향이 얼마나 큰지, 여러 근거를 얼마나 종합해야 하는지를 각각 0~3으로 예측한다. 그다음 해당 요구를 충족하는 모델을 능력·가격 기준으로 선택한다. 특정 모델이 자주 선택됐다는 사실을 그대로 정답으로 외우는 구조를 분리하려는 변경이다. [초기 변경 `601c989`](https://github.com/yoonki1207/nodease/commit/601c989), [현재 판정 경로](https://github.com/yoonki1207/nodease/blob/9ad27d5abceb527fa32e6612ffe6b6917450cef5/apps/workflow_engine/services/model_router.py#L464)
2. **외부 Judge의 능력 평가와 모델 선택을 분리했다.** Judge에게 모델 이름이나 가격을 고르게 하는 대신 요청의 세 가지 요구 수준을 판정하게 했다. [변경 `d7735c1`](https://github.com/yoonki1207/nodease/commit/d7735c1)
3. **학습량과 정확성 조건을 강화했다.** 현재 전환 조건에는 최소 100개 학습 라벨, 최근 평가 50개, 각 축 정확도 85% 이상, 세 축 전체 일치율 75% 이상, 고위험 과소평가 0건 등이 포함된다. 서로 다른 정답을 하나로만 예측하는 경우도 차단한다. 이는 전환을 시도할 최소 조건이지, 100개면 반드시 학습이 끝난다는 보장은 아니다. [현재 전환 조건](https://github.com/yoonki1207/nodease/blob/9ad27d5abceb527fa32e6612ffe6b6917450cef5/apps/workflow_engine/services/model_routing_incremental_learning.py#L546)
4. **학습 중인 후보와 실제 사용 버전을 분리했다.** 검증을 통과한 버전만 게시하고 실제 정책에 연결한다. 이후 후보가 추가로 학습돼도 사용 중인 버전이 곧바로 바뀌지는 않는다. 자신감이 낮거나 점검 대상으로 선정된 요청은 외부 Judge로 돌린다. [변경 `1546817`](https://github.com/yoonki1207/nodease/commit/1546817), [행위·근거 신호 보강 `9bb0d3f`](https://github.com/yoonki1207/nodease/commit/9bb0d3f)

이 변경으로 확인된 것은 **검증이 부족한 분류기로 성급하게 전환하지 않도록 했다는 점**이다. 정확한 로컬 라우팅 자체가 완성됐다고 단정할 수는 없다.

**4. 이번에는 어떻게 검증했나**

합성 요청 450개를 고정하고 300개는 학습, 150개는 평가에만 사용했다. 평가 요청은 학습에 사용한 문장을 이름만 바꾼 형태가 되지 않도록 문제 구성을 달리했다. 세 가지 난이도를 균등하게 넣고, 같은 학습 자료의 순서를 세 번 바꿔 결과가 순서에 좌우되는지도 확인했다. 세 번 모두 같은 150개 평가 자료를 사용하므로 독립적인 평가 사례가 450개 생긴 것은 아니다.

실제 고정 버전 E5 인코더와 운영 학습 코드를 사용했다. 첫 실험은 작성해 둔 기대 정답을 학습시켰고, 두 번째는 실제 `gpt-5.4-mini` Judge가 300개 요청을 판정한 결과를 학습시켰다. 평가 정답은 학습에 넣지 않았다. [데이터·코드 해시와 기준](/Users/hong-yoonki/Desktop/krafton/final-project/yoonki1207-nodease/reports/model-routing/verification/2026-09-21/manifest.json)

| 새 실험 | 각 축 정확도 | 세 축 전체 일치율 | 최고 영향도 사례를 낮게 평가한 수 | 전환 조건 판정 |
|---|---:|---:|---:|---|
| 작성된 기대 정답으로 학습 | 30.0~43.3% | 0~10% | 세 순서 모두 35/35 | 세 순서 모두 외부 Judge 유지 |
| 실제 Judge 정답으로 학습 | 30.0~43.3% | 세 순서 모두 0% | 세 순서 모두 35/35 | 세 순서 모두 외부 Judge 유지 |

작업 복잡도는 모든 실험에서 한 값으로만 예측했다. 근거 종합도도 대부분의 실험에서 한 값으로 굳어졌다. 전체 세 축 조합은 3~4종류여서 ‘모든 예측이 정확히 한 종류’인 상태는 아니었지만, 개별 축에서는 여전히 구분 능력이 부족했다. [저장된 예측에서 재계산한 수치](/Users/hong-yoonki/Desktop/krafton/final-project/yoonki1207-nodease/reports/model-routing/verification/2026-09-21/classification-summary.json)

두 실험의 **분류기 판정은 FAIL**, 전체 서비스 검증 판정은 **INCOMPLETE**다. 후자는 결과를 숨기는 표현이 아니다. 이번 두 실행은 분류기의 학습·일반화를 검사했으며, 게시된 분류기로 실제 워크플로 답변을 생성하고 품질까지 평가한 전체 실행은 아니기 때문이다. 실제 로컬 선택 비율이나 답변 품질이 검증됐다고 보고하지 않았다.

표의 전환 판정은 실행·출력 형식·후속 처리 성공률을 이상적인 값으로 가정해 운영 코드의 조건 함수를 평가한 진단이다. 이 유리한 가정에서도 정확도 조건을 통과하지 못했다. 실제 DB에서 버전 게시를 시도한 결과와는 구분해야 한다.

실제 Judge 호출은 300회 모두 성공했다. 사용량이 확인되지 않은 호출과 실패 호출은 없었고, 토큰 사용량에 따른 추정 비용은 **$0.422541**로 승인된 $30 이내였다. 청구서 확정 금액은 아니다. [실제 호출 실험 결과](/Users/hong-yoonki/Desktop/krafton/final-project/yoonki1207-nodease/reports/model-routing/verification/2026-09-21/live-judge.json)

**5. 코드·DB 검증이 증명하는 범위**

별도의 원격 PostgreSQL 테스트에서 검증된 버전의 게시, 정책 연결, DB 재조회, 실제 라우터가 게시 버전을 소비하는 경로를 확인했다. 이 테스트는 DB 연결 동작을 분리해 검사하기 위해 예측값과 운영 성공률을 대체한다. 따라서 이 테스트 통과를 실제 분류 정확도 증명으로 사용하지 않았다.

또한 외부 Judge가 모든 요청을 처리한 실행이 성공으로 둔갑하지 않는지, 평가 중 학습 상태가 바뀌지 않았는지, 평가 누락·정답 변조·모델 정보 누락이 차단되는지, 한 축만 상수로 굳어지는 경우를 감지하는지 확인했다. 최종 로컬 결과는 69개 통과·PostgreSQL 1개 생략이며, 원격에서는 PostgreSQL을 포함해 70개가 모두 통과하고 생략은 없었다. [최종 CI 실행](https://github.com/yoonki1207/nodease/actions/runs/35524570927)

원격 CI 결과와 실행한 테스트 목록은 [CI 증거](/Users/hong-yoonki/Desktop/krafton/final-project/yoonki1207-nodease/reports/model-routing/verification/2026-09-21/remote-ci.json)에 저장했다.

요구 수준을 맞혔는데도 그 요구에 맞지 않는 모델을 선택한 경우 역시 합격하지 못하게 했다. 모든 모델을 같은 비율로 쓰게 강제하지는 않는다. 현재 고정 후보 3개에 기대 정답과 선택 규칙을 적용하면 사용될 모델은 2종류다. 이 확인은 기존 선택 함수에 기대 정답을 넣어 비교하므로, 선택 함수 자체를 독립적으로 검증한 실험은 아니다.

전체 실제 워크플로 실험을 위한 실행 도구도 구현했다. 새 UUID로 별도 자원을 만들고 300건 학습 후 실제 게시 여부를 확인하며, 준비되지 않으면 비싼 품질 평가를 시작하지 않는다. 준비된 경우에만 고정된 150건을 중간·고성능 모델과 비교한다. 현재 설정된 로컬 DB에 접속할 수 없었고 저장소 규칙상 PostgreSQL 통합 검증은 원격 CI에서 수행하므로, 이 전체 실제 실행은 하지 않았다. **판단의 한계와 남은 작업**

기대 정답은 이번 검증을 위해 작성한 기준이며 독립된 전문가들이 합의한 정답은 아니다. 자료는 15개 업무 영역의 합성 문제이고, 학습과 평가에 동일한 업무 영역이 포함된다. 이번 실패는 이 고정 자료와 선택한 코드 버전에 대한 결과다. 모든 실제 요청의 실패율로 일반화할 수 없다. 실제 Judge 라벨과 기대 정답의 차이를 별도 저장·분석하지 않았으므로, 실제 Judge 실험의 오류를 학습기와 라벨 차이에 정확히 분배하지도 않았다.

다음 개선에서는 정답 기준의 독립 검토, 충분한 평가용 라벨 보존, 학습 특징과 학습량의 대조 실험이 필요하다. 그 결과를 바탕으로 분류기를 고친 뒤, 아직 사용하지 않은 별도 평가 자료와 실제 게시·답변 품질 경로를 다시 검증해야 한다. 이번 결과를 보고 합격선을 낮추거나 운영 알고리즘을 임의로 조정하지 않았다.
