# Nodease 실패 한계 탐색 부하 테스트 결과

2026-09-22 · 실제 시험 및 복구 확인 17:38~18:27 KST

**3.75 RPS는 이번 단일 회차의 기준을 통과했고, 4.375 RPS에서는 DB 연결 고갈과 실행 기록 손실이 발생했다. 10분 뒤에도 기록이 회복되지 않아 계획에 따라 후속 시험을 중단했다. 일반 Nodease와 Grafana는 복구·접속 확인을 마쳤다.**

## 시험 조건

- 전용 `nodease-loadtest` 프로젝트·DB·Redis·업로드 볼륨. 일반 데이터 볼륨과 분리했다.
- 워크플로우: Start → HTTP mock 10초 대기 → Answer. 외부 LLM·RAG·Sandbox 호출 없음. 같은 정의의 여러 run을 실행했다.
- Docker: CPU 8개, 메모리 8,215,117,824바이트(약 7.65 GiB). PostgreSQL `max_connections=100`.
- 단일 workflow worker의 설정은 gevent concurrency 100, SQLAlchemy 풀은 프로세스별 기본 20 + 추가 30이다. 시험 중 이 설정을 바꾸지 않았다.
- API 발생기는 응답 지연과 독립적으로 요청 시작률을 유지했다. 최대 미완료 요청 300개, 요청 timeout 60초. 각 일반 단계는 준비 60초 + 측정 180초, 기준선·회복은 준비 60초 + 측정 240초다.
- 실패 기준: 측정 완료 100건 이상에서 오류율 >1% 또는 p95 >15초. 최근 30초 완료 20건 이상에서 timeout/5xx >20%이면 조기 중단. 정합성·환경 보호 기준은 계획을 따랐다.
- 체크아웃 HEAD: `2c6bda2f5e4bfe8c8c126278ca5dce13bd86f6f0`. 이미지 ID와 파일 지문은 로컬 원본에만 보관했다. 실제 이미지와 체크아웃 revision이 같다고 추정하지 않는다.

## 단계별 결과

표본은 측정 구간에 시작한 요청이다. B3만 준비 구간에서 조기 중단됐으므로 12.94초의 부분 표본이다. 평균·최대 동시 실행은 HTTP 미완료 수가 아니라 engine 시작·종료 이벤트로 계산했다.

모든 구간에서 예정 요청 누락과 정산되지 않은 HTTP 요청은 0건이었다. B3의 실제 시작률은 준비 구간 12.94초를 분모로 계산했다. 준비 구간 중단을 정상 성능 측정으로 취급하지 않았다.

3.75 RPS의 전체 요청은 준비 구간을 포함해 900건이며 모두 HTTP·DB 성공이었다. 4.375 RPS의 전체 요청은 1,050건이며 HTTP 200은 1,019건, HTTP 500은 31건이다. 표의 측정 구간 오류 20건과 전체 오류 31건은 집계 범위가 다르다.

## 실행 기록 정합성 실패

4.375 RPS 단계 종료 후 다음 불일치가 남았다.

| 대조 항목 | 결과 |
|---|---:|
| HTTP 성공 응답의 고유 run ID | 1,019 |
| 성공 응답은 있으나 DB run 기록 없음 | 146 |
| 성공 응답이 있으나 DB 상태가 RUNNING | 67 |
| DB SUCCESS / FAILED / RUNNING | 806 / 11 / 67 |
| DB 전체 run / 고유 입력 수 | 884 / 884 |
| 최종 실패한 `log.create_run` task | 147 |
| 최종 실패한 `log.update_run_finish` task | 213 |

성공 응답과 DB run ID는 SHA-256 해시로 대조했다. 로그 task 개수는 동일 task ID의 재시도를 중복 집계하지 않은 최종 실패 수다. task ID와 run ID의 직접 매핑은 수집하지 않았으므로 두 집합의 행별 인과관계를 확정하지는 않았다.

실제 엔진 이벤트는 전체 3,152개 시작 모두 종료 이벤트와 짝이 맞았다. C2 구간에도 종료 누락은 없었다. worker 3개의 active·reserved·scheduled 작업은 모두 0, Redis의 대상 우선순위 큐와 unacked 합계도 0이었다. 따라서 DB의 RUNNING 67건을 실제 동시 실행 67건으로 해석하면 안 된다.

## 실패 원인과 회복

Gateway·Workflow Engine·Log System·PostgreSQL에서 DB 연결 한도 초과 오류를 확인했다. 1 RPS 조회 시 트랜잭션을 연 채 대기하는 연결 22개가 있었고, 2.5 RPS에서는 51개였다. 5 RPS 최초 실패 구간에는 mock 오류·거절이 없었으며 VM 메모리 사용률 최대는 약 56.4%였다. 발생기 사전 검증도 통과했다. 이 증거는 DB 연결 고갈을 주된 병목으로 가리킨다.

현재 코드에서 이를 설명하는 경로는 다음과 같다.

1. Gateway는 요청 DB 세션을 유지한 채 Celery 결과를 기다린다. Workflow Engine도 기본 DB 세션을 유지한 채 10초 HTTP I/O를 수행한다. 외부 효과 검사와 trace 정책 조회는 추가 연결을 사용할 수 있다.
2. 성공한 3노드 실행 하나가 run 생성/완료와 node 생성/완료를 합쳐 8개의 독립 로그 task를 보낸다. 4.375 RPS이면 재시도 이전부터 약 35개 로그 task/초가 발생한다.
3. HTTP 응답은 종료 로그의 DB commit을 기다리지 않는다. 종료 로그는 최초 시도 후 최대 3회 재시도하며, 재시도가 소진된 RUNNING 기록을 자동 정리하는 경로는 확인되지 않았다. 이는 관측된 최종 로그 실패·기록 누락과 일치한다.

코드 근거: [Gateway 결과 대기](../../../../apps/gateway/services/deployment_service.py#L1224), [Gateway 세션 종료](../../../../apps/shared/db/session.py#L31), [workflow task 세션](../../../../apps/workflow_engine/tasks.py#L527), [비동기 로그 전송](../../../../apps/workflow_engine/workflow/core/workflow_logger.py#L186), [종료 로그 저장과 재시도](../../../../apps/log_system/tasks.py#L444), [재시도 지연](../../../../apps/log_system/tasks.py#L114).

5 RPS 조기 중단 후에는 자동 회복했다. 저부하 재검증 120건 오류 0, p95 10.66초로 최초 10.64초 대비 허용 20% 이내였다. 재시작은 하지 않았다.

4.375 RPS 이후에는 회복하지 못했다. 신규 요청은 18:15:08.946 KST에 종료됐고, 600.165초 뒤인 18:25:09.111에도 DB RUNNING 67건이 남았다. 요청 처리·큐가 비어도 실행 기록 정합성이 회복되지 않았으므로 회복 실패로 판정했다.

이에 따라 C3, 정상/실패 후보의 반복 측정, UI 25명 혼합 15분 시험, 남은 저부하 회복 비교는 실행하지 않았다. 실패 기록을 성공으로 덮어쓰거나 테스트 볼륨을 삭제하지 않았다.

## 사전 검증과 변경 범위

- 기존 짧은 template workflow 6건: HTTP·DB 모두 성공.
- io-10s 단건 보정 12건: 모두 성공, 응답 10.59~10.66초.
- mock 직접 발생기 검증: 18.75 RPS, 준비 10초 + 측정 120초. 측정 2,250건 오류 0, p95 10.02초.
- 제품 애플리케이션 소스는 변경하지 않았다. 시험용 fixture/mock, Compose overlay, 단계별 발생기·판정·계측·보호 도구와 관련 테스트만 추가했다. 일반 보안/egress 정책과 worker/DB 한도도 바꾸지 않았다.
- RED→GREEN으로 관련 도구를 검증했으며 최종 관련 단위 테스트는 **90 passed**였다. 기존 Pydantic/SWIG 경고만 있었다. 전체 저장소 회귀·원격 CI는 이번 범위에서 실행하지 않았다.
- A 이후에 관측 집계를 단계별로 제한하고 stop 파일을 원자적으로 게시하도록 보강했다. 준비 구간 중단도 실제 시작률을 검증해 경계 탐색에 사용할 수 있게 했다. 부하 발생 동작·실패 임계값은 바꾸지 않았으며 변경 지문은 로컬 원본에 보관했다.
- 30초 fixture는 현재 HTTP 노드의 30초 timeout 상한과 겹쳐 이번 실행기에 포함하지 않았다. F는 미실행이다.

## 일반 환경 복구

- 일반 Compose 프로젝트 `docker`로 복원했고 Nodease 페이지·API health·Grafana health가 모두 HTTP 200이다.
- collector가 컨테이너 11개를 정상 수집하며 Redis·Loki 연계도 정상이다.
- 기존 DB 볼륨 `docker_postgres_data`를 재사용했고 일반 DB RUNNING은 0건이다.
- `nodease-loadtest_postgres_data`, `nodease-loadtest_redis_data`, `nodease-loadtest_gateway_uploads`와 증거 파일을 보존했다.
- 전환 과정에서 기존 proxy의 이미지 ID를 로컬 저장소에서 조회하지 못해, 로컬에 남아 있던 `docker-proxy:latest`의 이미지 ID로 시험·복구했다. 다른 10개 서비스는 원래 이미지 ID를 유지했다. 이 차이는 로컬 원본의 이미지 기록에 명시했다.
- 시험용 계측 overlay는 일반 환경에 적용하지 않았고 절전 방지도 해제했다.

## 결과의 범위와 다음 작업

이번 한 회차에서 3.75 RPS 통과와 4.375 RPS 실패를 관측했다. **확정된 최대 처리 용량이나 운영 권장값은 아니다.** 경계 반복과 혼합 시험을 완료하지 못했고, 결과는 이 10초 I/O fixture·단일 Mac/Docker 구성에만 적용한다. LLM·RAG·CPU·Sandbox 워크로드로 일반화하지 않는다.

다음 수정 회차에서는 DB 세션이 외부 I/O를 기다리는 동안 연결을 점유하는 범위, Gateway/worker/log worker의 전체 연결 예산, 종료 로그의 멱등적 재처리와 누락 복구 경로를 검토해야 한다. 이번 시험 중에는 해당 제품 동작을 수정하지 않았다. 수정 후에는 별도 회차로 동일 단계와 혼합 시험을 재실행한다.
