# Nodease 실패 한계 탐색 부하 테스트 계획

작성일: 2026-09-21. 실행 기록: **2026-09-22, C2에서 회복 실패로 조기 종료·일반 환경 복구 완료**.

[실행 결과 보고서](results/2026-09-22-breakpoint/summary.md): 3.75 RPS 통과, 4.375 RPS에서 DB 연결 고갈과 실행 기록 손실. 남은 경계 반복·혼합 시험은 실행하지 않았다. 아래의 도구 준비 상태와 수치는 계획 작성 당시 기록이다. 실행에는 전용 도구를 보강했으며, 30초 fixture는 현재 HTTP timeout 상한과 겹쳐 지원하지 않는다.

이 계획의 목적은 부하를 올려 **마지막 정상 단계, 최초 실패 단계, 병목, 회복 시간**을 찾는 것이다. 아래 수치는 이번 탐색을 위한 제안이며 제품 SLA나 검증된 처리 용량이 아니다. 첫 실패를 관측하면 추가 부하 증가를 멈추고 증거 수집과 회복 검증으로 전환한다.

## 1. 계획 작성 당시 확인한 상태

- 코드 확인 기준 HEAD: `2c6bda2f5e4bfe8c8c126278ca5dce13bd86f6f0`. 실행 때에는 HEAD, 관련 미커밋 변경의 지문, 실제 이미지 digest, 설정을 다시 기록한다.
- 2026-09-17 확인한 호스트는 Apple M3 8코어 / RAM 16GB, Docker 할당은 CPU 8개 / 약 7.65GiB였다. 이번 문서 작성 중 서비스를 기동하거나 현재 할당을 재측정하지 않았다.
- 단일 workflow worker는 `gevent --concurrency=100`이다. 슬롯 100개는 실제로 100개를 안정적으로 처리한다는 보장이 아니다. 시험 중 이 설정을 바꾸지 않는다.
- SQLAlchemy 연결 풀은 engine별 기본 20 + 추가 30이다. 이 값은 전체 서비스가 공유하는 DB 연결 상한과 다르다. 실행 전 PostgreSQL `max_connections`와 서비스별 실제 연결 수를 기록한다.
- 이전 5분 혼합 시험은 짧은 provider-free workflow의 동시 실행 최대 4건을 관측했다. 그 결과를 이번 장시간 실행의 용량으로 환산하지 않는다.
- 계획 작성 당시 기본 실행기는 `ui/api/mixed`, API `0.35/1/3 RPS`, 요청 timeout 20초를 제공했다. 2026-09-22 시험에는 별도 breakpoint 도구와 `io-10s` fixture·단계별 판정을 구현해 사용했다. `io-30s` fixture는 HTTP 노드 timeout 상한과 겹쳐 구현·실행하지 않았다.

근거: [worker 실행 설정](../../docker/workflow_engine/docker-entrypoint.sh), [DB 연결 설정](../../apps/shared/db/session.py), [기본 실행기](run_scenario.py), [요청 계약](scenario_contract.py). 이전 혼합 시험 보고서는 로컬 `reports/20260916T130942Z_mixed_5m_observation/summary.md`에만 보관하며 이번 커밋에 포함하지 않는다.

## 2. 용어와 시험 단위

| 측정값 | 의미 |
|---|---|
| 예정 요청률 / 실제 시작률 | 초당 보내기로 한 요청과 실제 전송을 시작한 요청. 단계별로 둘 다 기록 |
| 미완료 요청 | 발생기가 응답을 기다리는 HTTP 요청. 실행 중 workflow와 동일하지 않음 |
| 대기 작업 | 아직 worker에서 시작하지 않은 작업. 예약·unacked 상태도 따로 기록 |
| 실제 동시 실행 | worker가 시작한 뒤 끝나지 않은 해당 시험 workflow run 수 |
| 완료 시간 | 요청 시작부터 결과 검증 완료까지. 큐 대기를 포함 |
| worker 대기 / 실행 시간 | 작업 enqueue→시작, 시작→완료를 분리한 시간 |

실제 동시 실행은 run/task ID별 시작·종료 이벤트로 계산한다. DB `started_at/finished_at` 구간의 겹침으로 사후 대조하되, DB에 기록되기 전 구간은 별도 측정한다. 10초 간격의 Grafana 스냅샷이나 Locust 사용자 수만으로 최대 동시 실행을 주장하지 않는다.

주 실험은 하나의 배포 workflow를 여러 번 실행한다. 이는 같은 정의의 **run 동시성** 시험이다. 서로 다른 workflow 정의 25개의 실행은 혼합 시험에서 별도로 다룬다. 100개의 서로 다른 graph를 시험했다는 의미는 아니다.

## 3. 사용할 워크플로우

| 이름 | 구성 / 목적 | 상태 |
|---|---|---|
| `template-short` | 기존 Start → Template → Answer. 인증·실행·결과 검증 확인 | 기존 fixture 재사용 가능 |
| `io-10s` | Start → HTTP 요청 → Answer. 전용 mock 응답이 약 10초 걸림 | 2026-09-22 시험에 사용 |
| `io-30s` | 같은 구조에서 mock 응답이 약 30초 걸림 | 미구현·미실행, 후속 시험 |

mock은 외부 유료 LLM 없이 I/O 대기를 재현하고 요청별 고유 marker를 되돌려준다. mock 자체의 실제 지연·동시 처리 수·오류도 측정한다. mock 포화는 Nodease 한계로 집계하지 않는다.

HTTP 노드·credential 요구사항·현재 egress/proxy 정책에 맞는 전용 시험 endpoint를 준비하고 단건으로 검증한다. 일반 환경의 보안 정책을 완화하지 않는다. 호환되는 fixture를 마련하기 전에는 장시간 시험을 시작하지 않는다. Sandbox에서 `sleep`하는 방식은 별도의 Sandbox 동시성 제한을 측정하므로 I/O fixture로 대체 사용하지 않는다.

실제 LLM·RAG·CPU 연산·Sandbox가 섞인 워크플로우는 이번 1차 한계 탐색에 포함하지 않는다. 결과는 이 fixture와 서버 구성에만 적용한다.

## 4. 이름으로 관리할 시험 목록

아래 ID는 계획 작성 당시의 시험 목록이다. 2026-09-22 실행에는 별도 breakpoint runner를 사용했으며, 이 ID는 CLI 별칭이나 Makefile target을 뜻하지 않는다.

| ID | 이름 | 내용 | 종료 조건 |
|---|---|---|---|
| A | `bp-smoke` | 기존 짧은 graph 검증, `io-10s` 단건/동시 1개로 2분 보정, 이어 0.5 RPS 기준선 측정 | fixture 지연·결과·계측 정상 |
| B | `bp-io10-stair` | 1→2.5→5→7.5→10→12.5→15 RPS 단계 상승 | 최초 실패 또는 로컬 보호 상한 |
| C | `bp-boundary` | B의 마지막 정상 RPS와 최초 실패 RPS 사이를 좁혀 재시험 | 정상/실패 경계 재현 |
| D | `bp-mixed-hold` | 마지막 확인된 정상 RPS의 80% + UI 25명, 15분 | 혼합 사용 시 안정성 판정 |
| E | `bp-recovery` | 부하 제거 후 drain, 단건 기능 시험, 저부하 재측정 | 회복 완료 또는 회복 실패 |
| F | `bp-io30-stair` | 30초 fixture로 B/C 반복 | 긴 작업에서도 같은 병목인지 비교 |

1차 실행 순서는 **A → B → E → C → E → D → E**다. F는 긴 작업이 필요한 후속 회차로 분리한다. A의 기준선은 준비 60초 + 측정 240초로, 약 120개 완료 표본을 확보한다. 이 기준선부터 실패하거나 표본이 부족하면 B에 진입하지 않고 fixture·발생기·기본 실행을 먼저 조사한다.

시간 예산은 A 약 7분 + B 최대 28분 + C 탐색/재현 최대 28분 + D 15분 + E의 저부하 확인 15분으로, **drain과 환경 전환을 제외하고 최대 약 93분**이다. 환경 전환과 정상적인 짧은 drain을 포함하면 1차 회차에 1.5~2시간을 확보한다. 각 drain이 10분 상한에 가까워지면 더 길어지며, 회복에 실패하면 나머지 시험을 중단한다. F는 이 시간에 포함하지 않는다.

## 5. B: 첫 실패까지 부하 올리기

응답이 느려져도 예정 요청률을 자동으로 낮추지 않는 발생 방식을 사용한다. 발생기가 부하를 유지하지 못한 경우는 별도 무효 판정한다. worker 수를 올리거나 서버를 재기동하며 한 실험 안에서 조건을 바꾸지 않는다.

발생기는 기존 spike 도구의 90개 슬롯을 그대로 사용하지 않는다. 최대 미완료 요청 300개를 수용하도록 준비한다. B7의 `15 RPS × 허용 완료 시간 15초 × 여유 1.25 ≈ 282개`, F 마지막 단계의 `5 RPS × 45초 × 1.25 ≈ 282개`를 기준으로 잡은 제안이다. 긴 timeout까지 모두 점유되면 이 상한을 넘을 수 있으므로 300개 도달은 발생기 한계로 분리한다. 구현 후 Nodease를 거치지 않는 mock 대상 사전 검증에서 최대 목표의 1.25배 요청률을 2분간 유지할 수 있는지 확인하고, 실제 시험에서도 스케줄 지연을 관측한다.

| 단계 | 목표 요청 시작률 | 평균 실행 10초이고 대기가 없을 때 기대하는 동시 실행 수준 |
|---|---:|---:|
| B1 | 1 RPS | 약 10개 |
| B2 | 2.5 RPS | 약 25개 |
| B3 | 5 RPS | 약 50개 |
| B4 | 7.5 RPS | 약 75개 |
| B5 | 10 RPS | 약 100개 |
| B6 | 12.5 RPS | 125개 상당의 수요. 현재 100슬롯에서는 대기 발생 가능 |
| B7 | 15 RPS | 150개 상당의 수요. 실제 실행과 큐 대기를 구분 |

이는 평균 실행 시간으로 계산한 수요이며 실제 동시 실행 보장값이 아니다. 각 단계는 **준비 60초 + 측정 180초**로 구성한다. 준비 중에도 심각한 오류와 보호 기준은 적용한다. 정상 단계를 마칠 때마다 새 요청을 멈추고 이전 작업을 drain한 뒤 다음 단계로 이동한다. 단계 시간대와 요청 ID를 유지하여 이전 단계의 늦은 완료를 다음 단계 통계에 섞지 않는다.

최종 성능 통계는 측정 구간에 **시작한 요청 집합**을 기준으로, 이후 늦은 완료와 timeout까지 정산한다. 진행 중인 요청을 제외해 단계가 통과한 것처럼 보이게 하지 않는다. drain 종료 후 수락/완료 여부가 불명확한 요청이 남으면 해당 단계를 정상으로 판정하지 않는다. 실행 도중의 이동 구간 지표는 조기 중단 판단용으로 별도 보관한다.

최초 실패 이후 B의 다음 단계는 실행하지 않는다. B7까지 통과하면 “한계 미발견, 이번 구성에서 15 RPS까지 관측”으로 남긴다. 실패를 만들기 위해 맥북 보호 상한을 제거하지 않는다.

F는 같은 동시 수요 수준을 목표로 약 `0.33 → 0.83 → 1.67 → 2.5 → 3.33 → 4.17 → 5 RPS`를 사용한다. 단계별 완료 표본이 100개 미만이면 측정을 최대 5분까지 연장하며, 여전히 부족하면 해당 백분위·오류율 판정을 잠정으로 표시한다.

F 전에는 30초 fixture의 단건 보정과 별도 저부하 기준선도 준비한다. 기준선은 약 0.17 RPS, 준비 60초 + 측정 10분으로 100개 이상 완료 표본을 확인한다. F의 회복 비교에는 이 기준선을 사용하며 10초 fixture의 기준선과 혼합하지 않는다.

## 6. 무엇을 실패로 볼 것인가

성능 경계, 기능 실패, 환경/발생기 한계를 구별한다. 아래 기준은 시험 시작 전에 설정 파일에 고정할 **제안 기준**이며, 결과를 본 뒤 통과하도록 기준을 변경하지 않는다.

| 구분 | 기준 | 처리 |
|---|---|---|
| 기능 실패 | 응답 marker 불일치, 다른 실행 결과 혼입, 자동 재시도가 없는 요청의 중복 실행 | 1건부터 신규 요청 중단, 정합성 증거 수집 |
| 오류 경계 | 측정 구간 완료 요청 100개 이상에서 HTTP/네트워크/timeout/결과 검증 실패율 >1% | 해당 단계 실패, 상승 종료 |
| 빠른 오류 중단 | 최근 30초 20건 이상에서 timeout 또는 5xx >20% | 단계 종료 전이라도 신규 요청 중단 |
| 지연 경계 | 최소 100개 완료 기준, 완료 시간 p95가 `io-10s: 15초`, `io-30s: 45초` 초과 | 해당 단계 실패, 상승 종료 |
| 대기 경계 | 큐의 가장 오래된 시험 작업 대기가 `io-10s: 5초`, `io-30s: 15초`를 30초 연속 초과 | 처리량 포화로 기록, 상승 종료 |
| 서비스 장애 | 핵심 컨테이너 종료·OOM·예상 밖 재시작, 또는 health 5초 간격 3회 실패 | 신규 요청 즉시 중단, 회복 절차 |

429 등 명시적 거절은 사용자 관점 실패율에 포함하되 5xx와 분리한다. 이는 과부하 제어가 작동한 결과일 수도 있으므로 곧바로 프로그램 결함으로 단정하지 않는다. CPU 100%만으로 실패 판정하지 않고 처리 지연·오류·대기와 연결한다.

HTTP timeout은 `io-10s: 60초`, `io-30s: 90초`로 제안한다. HTTP 노드·proxy·Gateway·task의 관련 timeout도 먼저 대조한다. 정상 30초 작업을 기존 클라이언트의 20초 timeout으로 실패시키지 않는다. 클라이언트 timeout 이후에도 서버 작업이 계속될 수 있으므로 자동 재시도하지 않는다.

## 7. 맥북과 발생기 중단 기준

- 실행 전 전원 연결, 절전 방지, Docker 자원 고정, 무관한 고부하 작업 중지를 확인한다. 시험 종료와 복원 검증까지 절전 방지를 유지한다.
- 원래 Nodease와 분리한 `nodease-loadtest` 데이터만 사용하고 볼륨을 삭제하지 않는다. 기존 환경의 RUNNING·우선순위 큐·unacked가 비어야 전환한다.
- Docker VM 전체 메모리 압박을 측정한다. 컨테이너 memory percentage의 분모를 더해 VM 사용률로 오인하지 않는다. 컨테이너에 실제 제한이 있을 때만 해당 제한 대비 비율을 사용한다.
- VM 메모리 사용률 90% 이상이 30초 지속되거나 macOS 메모리 압박이 critical로 10초 지속되면 신규 요청을 중단한다. 발생 시 판정은 `host_resource_limit`로 분리한다.
- 시험 큐 대기 200건 초과 30초 또는 발생기 미완료 요청 300건 도달 시 중단한다. 후자는 `loadgen_limit`이며 Nodease 처리 한계로 확정하지 않는다.
- 측정 구간 실제 시작률이 목표의 95~105%를 벗어나거나, 예정 요청 누락·발생기 대기슬롯 고갈이 있으면 목표 부하 시험을 무효로 표시한다. 전송 스케줄 지연 p99 >250ms가 30초 지속돼도 발생기 원인을 조사한다.
- 발생기 CPU·메모리·스케줄 지연, mock 응답 지연을 별도로 기록한다. 이들이 먼저 포화되면 해당 한계를 해결한 뒤 같은 단계를 재시험한다.
- 관측 지표가 30초 이상 갱신되지 않으면 `observation_lost`로 중단한다. 관측 불가 상태에서 계속 부하를 올리지 않는다.
- B/F 각각은 최대 45분으로 제한한다. 보호 상한이나 시간 제한으로 끝난 결과는 “서비스 최초 실패점 미확정”으로 남긴다.

## 8. C: 실패 경계 좁히기

예를 들어 5 RPS 통과, 7.5 RPS 실패라면 6.25 RPS부터 시험한다. 같은 준비·측정·drain 조건으로 정상/실패 사이를 좁히며 **최대 3번 또는 구간 폭 10% 이내**가 되면 탐색을 끝낸다.

마지막 정상 후보와 최초 실패 후보는 독립된 구간으로 총 2회씩 측정해 재현성을 확인한다. 이미 측정한 유효 구간은 횟수에 포함한다. 재현이 안 되면 하나의 숫자를 확정하지 않고 범위와 환경 변동을 보고한다. 최초 단계부터 실패했다면 A의 단건 검증 결과를 기준으로 낮은 RPS로 내려가 정상 구간을 먼저 찾는다.

D의 80%는 확인용 출발점이다. 혼합 시험도 통과해야 해당 혼합 시나리오의 운영 후보로 삼을 수 있으며, 15분 통과를 장시간 안정성 보장으로 표현하지 않는다.

## 9. E: 실패 후 회복과 환경 복원

1. 신규 요청을 중단하되 DB·Redis·worker는 유지한다. 실제 오류·큐·메모리·task 상태를 먼저 보존한다.
2. 신규 요청 중단 시각을 고정하고 단계 종료 후 완료도 원래 요청의 단계에 귀속한다. 마지막 HTTP 요청을 `io-10s: 최대 60초`, `io-30s: 최대 90초`까지 기다린다. 이 시간은 전체 drain 상한 10분에 포함된다. 클라이언트 timeout 후에도 서버 작업의 성공·실패·RUNNING을 추적한다. 중단 시각부터 10분 뒤에도 남으면 미해결 요청 수를 남기고 회복 실패로 기록한다.
3. 큐·unacked·실행 중 작업이 0인 상태를 연속 두 번 확인한다. 단건 실행 성공과 health 정상도 확인한다.
4. A의 0.5 RPS 저부하를 준비 60초 + 측정 240초로 재실행한다. 오류 0건, 큐 비누적, 완료 시간 p95가 A의 유효한 기준선 대비 20% 이내면 회복으로 판정한다. B1 자체가 실패해도 A를 비교 기준으로 쓸 수 있다. F는 앞서 확보한 30초 fixture 기준선의 부하와 측정 시간을 재사용한다. 장애 때부터 이 조건 충족까지의 시간을 기록한다.
5. 자동 회복과 재시작이 필요했던 회복을 구분한다. OOM·DB 중단 등으로 수동 복구가 필요하면 해당 회차는 종료하고, 복구 전후 결과를 같은 연속 시험처럼 합치지 않는다.
6. 기존 일반 환경과 collector 네트워크를 복원한다. Nodease 페이지·API health·Grafana와 최신 수집 상태, 기존 DB 볼륨을 확인한다. 컨테이너 healthy만으로 호스트 접속 성공을 대신하지 않는다.

전환이나 seed가 실패한 경우도 원래 환경 복원 경로를 실행한다. 서버에 남은 시험 작업을 증거 없이 삭제하거나 원래 데이터 볼륨을 초기화하지 않는다.

## 10. 실행 전 필요한 최소 보강 (계획 작성 당시)

아래 목록은 계획 작성 당시의 준비 항목이다. 2026-09-22 회차에서는 10초 fixture와 전용 발생기·관측·중단·복원 도구를 구현·검증했다. 30초 fixture와 F 시험은 수행하지 않았다. 실제 수행 결과와 한계는 위 실행 결과 보고서를 따른다.

1. 위 scenario ID를 선택하는 설정과 단계별 RPS·fixture·측정 시간·timeout·중단 기준을 추가한다. Makefile 별칭은 이 설정을 호출하는 얇은 진입점으로 둔다.
2. `io-10s/io-30s` fixture와 지연을 검증하는 mock을 준비한다. 단건 시험에서 지연 원인과 marker 일치를 검증한다.
3. 예정/실제 시작·응답 완료·미완료·누락을 기록하고, 서버가 느려져도 목표 요청률을 유지할 수 있는 발생기를 준비한다. 유한 상한 도달은 무효 사유로 기록한다.
4. enqueue·실행 시작·종료·큐 나이·실제 실행 동시성·DB 연결 대기를 계측한다. 기존 관측 기능으로 얻을 수 없는 값은 필요한 계측 추가를 먼저 검토한다. 누락된 값을 추정치로 채우지 않는다.
5. 첫 실패·발생기 무효·호스트 중단을 구분하고 drain/복원을 보장하는 실행 절차를 마련한다. 기존 spike 도구의 고정 1→3→1 RPS를 이번 계획으로 오인하지 않는다.
6. 전용 fixture/설정 검증과 실패·timeout·중단·중복 정산 경계를 테스트한다. 제품 코드 변경이 필요한 부분만 TDD로 최소 수정한다.

## 11. 결과로 남길 것

결과 폴더는 `<UTC timestamp>_<scenario ID>`로 구분한다. 시험 조건은 실행 시작 전에 저장하고 단계 경계 시각도 남긴다. credential·token·응답 본문·raw payload는 결과 파일에 쓰지 않는다.

| 단계 | 목표/실제 RPS | 실제 실행 평균/최대 | 대기 p95 | 완료 p95/p99 | 실패율 | 종료 이유 |
|---|---|---|---|---|---|---|
| B1 … | 측정값 | 이벤트 + DB 대조 | 측정값 | 측정값 | 오류 종류별 | 정상/서비스 경계/환경 한계/무효 |

별도로 시작한 요청 수, 고유 run ID, DB 최종 상태, timeout 후 완료, 중복 실행, 응답을 못 받아 수락 여부가 불명확한 요청을 정산한다. 요청 ID는 원문 대신 해시 등 비민감 식별자로 남길 수 있다. 준비 구간도 정산에는 포함하되 성능 통계와 분리한다. 클라이언트 연결 실패를 자동으로 “서버 실행 없음”으로 판단하지 않는다.

최종 보고서는 **정상 범위 / 최초 실패 범위 / 실패 종류와 병목 근거 / 자동 회복 여부와 시간 / 마지막까지 확인하지 못한 한계**를 제시한다. 병목 수정이나 worker 증설 후에는 별도 회차로 비교한다.

## 12. 참고와 문서 범위

- Grafana는 트래픽을 점진적으로 높여 실패 지점을 찾는 시험을 breakpoint test로 구분한다. 도구는 기존 Locust를 유지하고 시험 설계 개념을 참고한다. [API load testing](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)
- 발생기 자체의 자원 포화가 측정 결과를 왜곡할 수 있어 별도로 관측한다. [Running large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)
- 이 파일은 특정 revision을 참고해 작성한 역사적 실행 계획이며 제품 명세나 릴리즈 승인 근거가 아니다. 작성 당시에는 구현·부하 실행이 없었으나 2026-09-22에 별도 회차를 실행했다. 결과와 미실행 범위는 위 보고서를 따른다.
